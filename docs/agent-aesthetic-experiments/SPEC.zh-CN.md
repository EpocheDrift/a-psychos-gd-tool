# Agent × MCP 平面设计审美实验规约

状态：**Active working specification**

版本：**0.2.0**

生效日期：**2026-07-28**

最近修订：**2026-08-03**

规范所有者：**项目所有者**

适用项目：**GraphicDesign-Assembler / a-psychos-gd-tool**

## 1. 文档地位

本文档是本项目进行 Agent × MCP 审美与人机协作实验时的唯一规范来源
（single source of truth）。它定义研究意图、实验边界、评价方法、执行流程和
记录要求。

每次实验必须创建独立 Session 记录，并在开始操作前写明研究问题、固定条件、
变量、主要结果指标和停止规则。看到结果后，不得静默改变这些内容。确需调整时，
必须：

1. 停止当前实验，保留已产生的结果；
2. 在 Session 记录中说明偏离原因；
3. 更新本文档版本或明确标记一次预先声明的例外；
4. 以新的 Session 或 Run ID 重新开始。

本文档中的“必须”“不得”是实验有效性的强约束；“建议”是默认做法，偏离时应在
Session 记录中解释。

本文档只约束**正式实验**，不应强迫普通设计协作进行完整预注册。日常协作以
[`collaborate-on-graphic-design`](../../.agents/skills/collaborate-on-graphic-design/SKILL.md)
为操作性来源；当前研究状态、公开证据和限制见
[`README.md`](./README.md)。Spec 决定实验有效性，Skill 决定普通协作行为，二者不得
互相冒充。Spec 由独立 custodian/evaluator 持有；因为它包含评价维度和 protocol
expectations，不得直接进入计数 Run 的 runner context。custodian 只能据此派生不含评价
规则、历史结果或预期诊断的最小 runner packet。

## 2. 研究目的

本研究不以证明 MCP 的基础连通性为主要目标。基础连通性、schema、事务、权限、
revision、render 和 preview 的正确性由现有工程测试负责。

本研究关注从设计意图到视觉结果的完整链路：

```text
人类意图与需求表达
  → Agent 对需求的解释
  → Agent 的设计策略与操作计划
  → MCP 语义操作
  → 实际渲染结果
  → Agent 与人类评价
  → 反馈和修订
  → 最终审美结果
```

核心目标是回答：

1. 人应如何描述 Graphic Design 需求，才能传达真正的审美意图？
2. Agent 如何把抽象语言翻译为层级、构图、字体、色彩、节奏和图像处理决策？
3. 哪种人机交互方式最容易以较低成本收敛到目标审美？
4. MCP 的工具粒度、状态反馈和视觉证据如何影响 Agent 的创作与修正能力？
5. 哪些质量可以自动检查，哪些必须依赖人类判断？
6. 如何提高审美质量的稳定性，而不把结果收缩成同一种安全模板？

## 3. 明确区分的四类结果

每次分析必须分别报告以下结果，不得用“成功”一词将它们混为一谈：

1. **执行可靠性**：调用是否合法，事务、权限、revision 和渲染是否正确。
2. **需求符合度**：结果是否实现内容要求、使用目标和用户意图。
3. **审美质量**：视觉层级、构图、字体、色彩、统一性、独特性和完成度。
4. **协作效率**：达到结果所需时间、调用、revision、反馈和人工介入。

`gfx_validate_document`、成功事务和成功渲染只能证明执行可靠性，不能证明需求
符合度或审美质量。截图是评价证据，不是设计文档的权威状态。

## 4. 非目标

本规约暂不试图：

- 宣称存在完全客观、跨文化的单一审美分数；
- 用自动视觉模型取代人类审美判断；
- 通过一次成功案例证明某种交互方法普遍有效；
- 把工程正确性、渲染成功或“没有明显错误”等同于高质量设计；
- 追求像素级复刻未获授权的设计作品；
- 在未记录的情况下比较不同 Agent 模型、版本或系统提示；
- 为获得高分而固定成单一“高级、极简、黑白、大字”模板；
- 因工具暂不支持某种视觉语言，就把它解释为 Agent 不理解该语言。

## 5. 初始研究问题与假设

### 5.1 研究问题

- **RQ1 — Brief 表达**：自然语言、结构化 Brief、参考图和反例分别贡献什么？
- **RQ2 — 意图翻译**：让 Agent 先陈述设计策略，是否提高需求符合度和审美质量？
- **RQ3 — 视觉闭环**：基于准确 revision 的预览迭代，是否优于一次性生成？
- **RQ4 — 反馈语言**：感受词、关系描述和精确参数分别适合解决什么问题？
- **RQ5 — 自主程度**：人类在哪些节点介入最有效，何时介入反而限制探索？
- **RQ6 — 自我批评**：Agent 的分层自评能否减少工艺缺陷，是否会降低独特性？
- **RQ7 — MCP 粒度**：原子低层 transaction 是否足够，何时才需要更高层工具？
- **RQ8 — 稳定性**：同一 Brief 多次运行时，质量和意图符合度的方差有多大？

### 5.2 待验证假设

以下是假设，不是预设结论：

- **H1**：结构化 Brief 会提高需求符合度，但不一定自动提高独特性。
- **H2**：Agent 在执行前明确设计策略，会减少方向性返工。
- **H3**：预览后的有限轮次修订会提高完成度，但过多轮次可能使设计趋于保守。
- **H4**：“感受 + 视觉关系 + 原因”的反馈比单独使用模糊形容词更有效。
- **H5**：缩略图评价更容易发现层级问题，大图评价更容易发现字体和工艺问题。
- **H6**：人类负责目标与取舍、Agent 负责展开与执行的混合流程，优于完全单方控制。
- **H7**：精确 revision、原子事务和稳定 request ID 会提高实验可信度，但本身不会
  直接提高审美质量。

## 6. 实验原则

### 6.1 单变量原则

正式对比中一次只改变一个主要变量。若同时改变 Agent 模型、Brief、工作流和反馈
轮数，该结果只能标记为探索性案例，不得用于因果判断。

### 6.2 预先声明

每个正式 Session 必须在第一笔设计写入前固定：

- 研究问题和假设；
- 任务与内容；
- 对比条件；
- 控制变量；
- 主要结果指标；
- 修订轮数或停止规则；
- 评价者是否知晓条件；
- 重复次数。

### 6.3 干净起点

对比 Run 应使用相同的初始文档、frame、字体可用性、资产、Agent 权限和 MCP
capability 版本。默认新建实验图层，不修改已有作品。需要继承前一版时，必须把
“继承设计”作为条件的一部分。

### 6.4 重复与盲评

- Pilot 可以每个条件运行 1 次，但只用于调试协议。
- 正式方向性比较建议每个条件至少运行 3 次。
- 能做盲评时，不向评价者展示条件名称、Agent 解释或运行顺序。
- 不得只挑最好的一次作为该条件的代表；应报告全部 Run 和方差。

### 6.5 最小必要权限

根据任务逐步启用：

- 纯文字/形状实验：`read`、`preview`、`edit`；
- 图片实验：额外启用 `assets`；
- 固定 RMBG-1.4 实验：额外启用 `model`。

未使用的权限不应仅为了方便而开启。每次进程重启或配对重建后重新记录实际授权。

## 7. 标准任务族

| ID | 任务族 | 主要观察能力 | 默认权限 |
| --- | --- | --- | --- |
| T1 | 纯文字海报 | 层级、构图、字体角色、抽象风格语言 | edit |
| T2 | 信息密集活动海报 | 内容组织、阅读路径、约束满足 | edit |
| T3 | 图像主导的编辑设计 | 图文关系、裁切、图像处理、资产语义 | edit + assets |
| T4 | 同一视觉系统的系列变体 | 一致性、变化幅度、设计 token 的复用 | edit，可选 assets |
| T5 | 模糊或开放式艺术指导 | 澄清、假设、探索性和独特性 | edit，可选 assets |
| T6 | 诊断并改进现有设计 | 视觉批评、保留/改变判断、最小修订 | edit |
| T7 | 去背景与合成 | 模型节点的视觉价值和失败恢复 | edit + assets + model |

新增任务族前，应说明现有任务族为何不能覆盖该研究问题。

## 8. 可操纵变量与控制变量

### 8.1 可操纵变量

允许被明确比较的变量包括：

- Brief 形式：短自然语言、结构化 Brief、对话式 Brief；
- 视觉参照：无参考、参考图、情绪板、反例；
- Agent 流程：直接执行、先解释后执行、多个候选策略后选择；
- 反馈类型：模糊感受、关系描述、精确约束、带区域指向的反馈；
- 人类介入：仅最终评审、方向确认、每轮确认、共同编辑；
- 自评方式：无自评、自由批评、固定 rubric、先合规后审美的两遍批评；
- 候选数量：单方案、并行多个方向、同方向多个变体；
- MCP 操作粒度：单个原子设计事务、多个目标化事务、未来高层 helper；
- 修订预算：固定轮数、固定时间、达到预先阈值时停止。

### 8.2 必须记录的控制变量

- Agent 产品、模型和可见版本；
- 系统/开发者约束中会影响设计行为的部分；
- MCP Companion 版本与 capability/protocol 版本；
- 浏览器、操作系统和视口环境；
- frame、固定文案、资产和字体条件；
- 初始 document revision 与图层状态；
- 可用 scope；
- 候选数、反馈轮数、时间预算；
- 是否允许 Agent 读取前一条件的结果。

无法固定的变量必须记录为混杂因素。

## 9. 标准 Graphic Design Brief

结构化 Brief 使用以下字段。实验可有意省略字段，但必须把“省略”作为条件记录。

```text
项目名称：

1. 目标
让谁在什么场景下产生什么感受、理解或行动？

2. 输出与场景
尺寸、比例、媒介、观看距离、是否需要系列化或缩略图表现。

3. 必须内容
完整文案、标志、图片、法律或品牌信息。

4. 信息层级
第一眼、第二眼、第三眼分别应该看到什么？

5. 审美意图
希望它显得怎样？这些词在本任务中具体指什么？

6. 视觉关系
紧张/舒展、秩序/混乱、克制/饱和、对称/偏置、平面/空间化等。

7. 视觉参考
参考什么，以及具体参考它的哪一部分；参考不是整图复刻指令。

8. 反例与避免项
不希望出现的风格、构图、效果、俗套和品牌误读。

9. 必须保留
不可改变的内容和视觉资产。

10. Agent 自由度
哪些部分可以大胆解释，哪些部分必须先询问或保持不变？

11. 验收信号
看到什么可观察现象时，可以认为目标达成？
```

只使用“高级、年轻、酷、现代、实验性”等形容词时，Agent 应把词翻译成可讨论的
视觉关系和设计选择，但不得假装这些词只有唯一视觉答案。

## 10. 标准 Agent × MCP 执行协议

除非实验条件有意改变某一步，每个 Run 遵循以下阶段。

本节规定实验顺序和证据纪律；当前工具名、参数、retry、render ticket、measurement、
asset 与 recovery 细节以冻结版本的
[`mcp-execution.md`](../../.agents/skills/collaborate-on-graphic-design/references/mcp-execution.md)
为准。若实时 capability 与参考文档不一致，应在设计写入前停止并记录，不得临时改动
条件后继续把该 Run 计入原实验。

### A. Preflight

1. 创建 Run ID。
2. 核对冻结的研究问题、主要结果、预算、停止规则和 runner allowlist。
3. 记录 Agent、Skill、MCP、浏览器、scope、环境和时间。
4. 调用当前 capability 与 document preflight，记录 baseline revision、frame 和 layers。
5. 确认 writable target 与其他 Run 隔离，并且不会覆盖非实验图层。
6. 确认 runner 无法读取 evaluator criteria、其他 Run、历史偏好或预期诊断。

### B. Brief 解释

Agent 输出：

- 对目标和受众的复述；
- 内容层级；
- 审美词到视觉关系的翻译；
- 关键设计决策；
- 明确假设和能力限制；
- 本 Run 不会尝试解决的内容。

如果该条件是“直接执行”，此阶段仍可写入内部 Session 记录，但不得向人类展示，
以免改变对照条件。

### C. 设计计划

Agent 在写入前记录预期的：

- 图层与节点结构；
- 构图骨架；
- 字体角色与文字层级；
- 色彩角色；
- 主要效果及其目的；
- 预期的阅读路径；
- 计划用大图还是缩略图验证哪些问题。

### D. MCP 写入

1. 在写入前封存本 Run 的策略与语义计划。
2. 使用当前 revision 对完整语义计划进行 dry-run，不把 dry-run 当成持久写入证据。
3. dry-run 后重新读取相关文档状态；若 revision 或依赖状态改变，先解释介入编辑，再
   重新计划和 dry-run。
4. 使用新的 request ID、最新 revision 和同一语义计划进行原子提交。
5. 不把编辑器节点位置误认为画面构图，也不因工具缺少某能力而静默更换研究问题。
6. 保留所有结构化错误、冲突和失败；只有预注册预算允许的技术修正可以继续。

### E. 精确渲染证据

1. 验证当前文档达到预注册的 renderable 条件。
2. 等待本次提交对应的准确 revision / render attempt。
3. 测量预注册的关键 rendered outputs，并获取准确 preview 证据。
4. 默认至少检查：
   - 接近 `1024px` 边长的大预览，用于细节与工艺；
   - 接近 `256px` 边长的缩略预览，用于层级与整体构图。
5. 在 private sealed record 中保存 revision、尺寸、hash、渲染状态和必要 reconstruction
   inputs；公开 ledger 只保留脱敏结果与不透明 archive key。

不得用旧 revision 的预览评价新事务。

### F. 两遍评价

第一遍只检查需求与硬约束：

- 文案和资产是否正确；
- 内容是否完整；
- 层级顺序是否符合 Brief；
- 是否违反必须保留和避免项；
- 是否存在技术或渲染错误。

第二遍再评价审美：

- 构图、比例、空间和视觉重心；
- 字体角色、节奏和可读性；
- 色彩关系；
- 视觉语言的一致性；
- 独特性和意图强度；
- 工艺完成度。

不得用“符合需求”替代审美评价，也不得因“好看”而忽略文案错误。

### G. 人类反馈与修订

默认反馈格式：

```text
保留：
改变：
原因：
本轮最高优先级：
允许 Agent 自由处理的部分：
```

Agent 应先把反馈翻译为准备改变的视觉关系，再执行目标化修订。除非反馈明确要求
推翻方向，否则应保留已确认的关系，避免每轮重新设计整张作品。

### H. 收尾

1. 验证最终 revision 和预览。
2. 记录最终评分、盲测偏好和开放式理由。
3. 记录工具调用、revision、修订轮数、失败与人工介入。
4. 区分“因预算停止”和“达到目标停止”。
5. 写出本 Run 能支持和不能支持的结论。

## 11. 审美质量评价

### 11.1 主要结果

正式对比的默认主要结果是：**不知道条件信息的人类评价者进行的成对偏好选择，
以及选择理由**。

维度分数是诊断工具，不应在没有预先声明权重时压缩成单一总分。若实验确需总分，
必须在看到结果前声明权重。

### 11.2 评分维度

每项使用 1–5 分，并写一句证据：

| 维度 | 1 分 | 3 分 | 5 分 |
| --- | --- | --- | --- |
| 需求符合度 | 明显偏离目标或内容错误 | 基本满足但有误读 | 准确实现且强化目标 |
| 信息层级 | 阅读顺序混乱 | 可读但层级普通 | 阅读路径清晰且有意图 |
| 构图与空间 | 失衡、拥挤或松散 | 稳定但缺少张力 | 比例、留白和重心有控制 |
| 字体与文字 | 字体角色和排版失效 | 可读但缺少精度 | 字体、尺度和节奏共同表达 |
| 色彩 | 对比或情绪不受控 | 功能正确 | 色彩有角色、统一且有辨识度 |
| 一致性 | 元素像偶然拼接 | 大体统一 | 形成完整、可解释的视觉系统 |
| 独特性 | 明显模板化 | 有少量个性 | 有记忆点且服务于意图 |
| 完成度 | 存在明显工艺缺陷 | 可交付但仍粗糙 | 细节、边缘和关系经过推敲 |

### 11.3 质量闸门

- **Q0 技术有效**：事务、validation、render 和 preview 对应准确 revision。
- **Q1 内容正确**：必须文案、资产和 frame 正确。
- **Q2 层级成立**：缩略图下仍能读出预期的第一/第二/第三层级。
- **Q3 构图成立**：视觉重心、边界、留白和元素关系有明确控制。
- **Q4 字体成立**：文字可读，字体角色、行长、行距和尺度关系服务目标。
- **Q5 色彩成立**：对比足够，颜色不是无目的装饰。
- **Q6 语言一致**：元素共享同一视觉逻辑，效果有可解释目的。
- **Q7 非模板化**：结果不只依赖默认的“大字 + 黑白 + 单一强调色”捷径。
- **Q8 证据完整**：Session 记录足以复查结论。

Q0–Q1 是硬门槛；Q2–Q7 是审美判断，不得宣称由代码“保证”。稳定的审美质量来自
明确 Brief、候选探索、视觉闭环、人类判断和可复查记录的组合。

## 12. 效率与过程指标

每个 Run 至少记录：

- MCP tool calls；
- 成功提交的 transaction 数；
- document revision 增量；
- human feedback rounds；
- Agent 自主修订轮数；
- validation/render/transport 失败；
- revision conflict、revert 和 retry；
- 从开始到最终选择的总时长；
- 人类直接指定参数或结构的次数；
- 被保留、局部修正和整体推翻的设计决策；
- Agent 自评与人类评价的一致和分歧。

调用更少不是独立目标；如果低调用数导致质量下降，应明确报告这种权衡。

## 13. Session 与 Run 记录

### 13.1 命名

- Session ID：`AE-YYYYMMDD-主题`
- Run ID：`<Session-ID>-<条件>-R<重复序号>`
- MCP request ID：`<Run-ID>-<动作>-V<序号>`，转换为工具接受的安全字符格式。

### 13.2 四个证据面

每个正式 Session 必须把以下材料逻辑或物理隔离：

1. **Runner packet**：只包含冻结的 Skill、任务 prompt、baseline、允许的公开/合成素材
   和该 Run 必需的 capability 信息。不得包含评价规则、旧结果、偏好方向或预期诊断。
2. **Private sealed record**：保存精确 Brief、全部 Run（包括失败）、原始或明确脱敏的人类
   反馈、环境 fingerprint、工具 trace、revision、资产身份、hash、preview、偏离和
   reconstruction inputs。它必须位于项目所有者批准且 runner 不可见的 evidence store。
3. **Evaluator packet**：保存 rubric、权重、expected assertions、随机展示标签、结果映射和
   evaluator notes；在计数 Run 完成并封存前不得向 runner 暴露。
4. **Public ledger**：只保存脱敏后的条件、观察、限制、协议偏离和不透明 archive key；不得
   保存私人图片、相机文件名、本地路径、source/output hash 或未经授权的逐字家庭场景
   对话。

公开目录中的 [`sessions/`](./sessions/) 是 v0.2.0 分层建立前产生的 legacy public
traces。当前 `main` 已隐藏已识别的私人 source 文件名、source hash 与家庭对话，但仍保留
output/reconstruction hashes 和相对 evidence paths；这是对既有公开工程来源的明确例外，
不是 v0.2.0 的未来存储标准。它们不得作为干净 forward Run 的输入。未来正式实验只向
本仓库提交 [`README.md`](./README.md) 中的脱敏 ledger 更新；完整记录进入 private sealed
store。

### 13.3 Private sealed record 的最小内容

每个正式 Session 至少保留：

- 研究问题、假设、任务族和冻结时间；
- 条件、控制变量、主要结果、预算、失败处理和停止规则；
- 完整 Brief、条件间实际差异和 runner allowlist；
- 每个 Run 的环境、baseline、策略封存、工具 trace 和 revision；
- 全部 preview、measurement、hash、失败和缺失 artifact；
- Agent 执行前策略与执行后评价；
- 人类反馈原文，或明确标记且不改变含义的脱敏版本；
- 盲评结果、维度评分、理由和 evaluator 映射；
- 偏离、混杂因素、不能得出的结论和下一步。

### 13.4 Public ledger 的最小内容

每个完成或停止的 Session 在公开 ledger 中只需记录：

- 不泄露私密内容的任务和条件摘要；
- primary outcome 是否可获得；
- 可支持的 Observation、Working rule 或 Hypothesis；
- 失败、偏离和限制；
- 若存在，经批准的不透明 private archive key。

不得把 private record 的缺失用更详细的公开披露补齐，也不得让公开 ledger 成为未来
runner 发现 evaluator expectations 或历史视觉 token 的入口。
